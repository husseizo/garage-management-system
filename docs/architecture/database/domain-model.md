# Domain model — Garage Management System

- **Status:** Phase 1A design baseline (2026-11-24)
- **Scope:** the complete planned system. Only the tables marked **1A** exist after this phase;
  everything else is design, implemented incrementally per
  [`migration-roadmap.md`](migration-roadmap.md).
- **Related:** [`erd.md`](erd.md) · [`data-dictionary.md`](data-dictionary.md) ·
  [`business-rules.md`](business-rules.md) · [`scheduling-model.md`](scheduling-model.md) · ADRs
  0008–0012.

## 1. Modelling principles

1. **Single garage (single tenant).** One deployment serves one garage. There is no `garage_id` on
   every row; garage-wide configuration lives in the singleton `garage_profile`. Multi-branch
   support is an open question (Q-01). Adding it later means one additive `location_id` column
   per location-scoped table, not a rewrite.
2. **Internal identity is a UUID** (`uuid`, generated by PostgreSQL 18 `uuidv7()`, time-ordered).
   Natural keys (phone, VIN, registration plate, booking reference) are attributes with their own
   constraints and are never primary keys (BR-01, BR-04). `staff_users` keeps its Phase 0 `cuid`
   text key. Changing it would be destructive and brings no benefit (ADR 0008).
3. **Requests are not commitments.** A booking _request_, an _appointment_ and a _job card_ are
   separate entities with separate lifecycles (BR-06).
4. **History is append-only where it matters.** Status changes, ownership, mileage, money and audit
   are recorded as new rows, never overwritten (BR-14).
5. **No generic polymorphic foreign keys.** Where several entities attach to one concept, we use
   either explicit join tables (`booking_attachments`, `job_card_attachments`) or a class-table
   supertype with real FKs (`scheduling_resources` for technicians and bays). The one deliberate
   exception is `audit_logs.entity_type/entity_id`: audit rows must outlive and span every table,
   so they reference entities by value (ADR 0012).
6. **Money** is `bigint` minor units plus an ISO 4217 `currency_code`. There are no floats.
7. **Time** is `timestamptz` (UTC instants). Local garage time is derived from
   `garage_profile.timezone`. Recurring calendars (working hours, shifts) store local wall-clock
   `time` plus weekday. Phase 0 `staff_users` uses `timestamp(3)` without a time zone. That is
   recorded as debt (R-04) and not changed in 1A.
8. **Normalised plus display values.** Phones are stored as E.164 (`+255712345678`). VINs and
   plates are stored both as the user's input and as a normalised search key.

## 2. Bounded contexts and module ownership

Each context maps to a module in `src/modules/*` (ADR 0001). Only the owning module writes its
tables. Other modules call its public API.

| Context                    | Module                       | Owns                                                                                                        |
| -------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------- |
| A. Identity & access       | `staff`, `customers`         | staff users, roles, permissions, customer verification, sessions, auth events                               |
| B. Customer management     | `customers`, `vehicles`      | customers, contacts, preferences, consent, vehicles, registrations, ownership                               |
| C. Booking management      | `bookings`                   | service catalogue, booking requests, requested services, status history, attachments, communications        |
| D. Smart scheduling        | `scheduling`                 | calendars, closures, technicians, skills, bays, capabilities, resources, appointments, reservations, holds  |
| E. Workshop operations     | `workshop` (future)          | job cards, tasks, inspections, findings, diagnostics, parts, work logs, QC, handover, paint production      |
| F. Quotations & finance    | `finance` (future)           | quotations, lines, approvals, invoices, payments, refunds, adjustments                                      |
| G. Customer retention      | `reminders`, `notifications` | service records, recommendations, mileage readings, reminder rules/schedules, templates, outbox, deliveries |
| H. Platform administration | `platform` (`src/server`)    | garage profile, system settings, audit logs, files, integrations, background jobs                           |

## 3. Entity catalogue

Legend: **1A** = implemented now · **P0** = exists from Phase 0 · other = target phase.

### A. Identity & access

| Entity                          | Table                              | Phase | Purpose                                                                            |
| ------------------------------- | ---------------------------------- | ----- | ---------------------------------------------------------------------------------- |
| Staff user                      | `staff_users`                      | P0    | Staff login identity (email, scrypt hash, active flag, legacy `role` enum)         |
| Role                            | `roles`                            | 1D    | Named role (Owner, Manager, Service advisor, Technician, custom)                   |
| Permission                      | `permissions`                      | 1D    | Fine-grained capability code, e.g. `booking.confirm`                               |
| Role permission                 | `role_permissions`                 | 1D    | M:N roles ↔ permissions                                                            |
| Staff role assignment           | `staff_role_assignments`           | 1D    | M:N staff ↔ roles with `granted_by`, `granted_at`, `revoked_at`                    |
| Customer verification challenge | `customer_verification_challenges` | 1C    | OTP challenge to a phone/email: hashed code, purpose, expiry, attempts             |
| Authentication session          | `auth_sessions`                    | 1C    | Server-side sessions (customers now; staff revocation later), token hash only      |
| Authentication event            | `auth_events`                      | 1C    | Sign-in success/failure, OTP sent/failed/locked, sign-out, for security monitoring |

Customer authentication has **no password**. A customer proves control of a verified contact
(OTP), which yields a short-lived `auth_sessions` row scoped to that customer (ADR 0011).

## 4. How identity, vehicles, bookings and workshop history relate

```
            (guest or signed-in)
booking_requests ──snapshot of contact + vehicle details──┐
      │ matched by staff (1C/1D), never automatically     │
      ▼                                                    ▼
  customers ──< customer_contacts                      vehicles ──< vehicle_registrations
      │                                                    │
      └──< vehicle_ownerships >────────────────────────────┘   (who owned it, when)
                                                           │
 appointments ── from 1 booking_request, for 1 vehicle ────┤
      │                                                    │
      └──1:0..1── job_cards ── for 1 vehicle, billed to 1 customer
                       │
                       ├─< job_card_tasks, inspections, diagnostics, parts, work logs
                       ├─< quotations ─< approvals        └─> invoices ─< payments
                       └─> service_records (per vehicle) ─> reminder_schedules
```

- **The vehicle is the anchor of history.** Service records, inspections and mileage readings hang
  off `vehicle_id`. A new owner sees the vehicle's service history (what was done, when, mileage)
  but not prior owners' names, contacts, invoices or communications (BR-05). That is enforced by the
  access layer: portal queries project service-history columns only and join through the
  _current_ `vehicle_ownerships` row.
- **The customer is the anchor of commercial relationships.** Job cards, quotations, invoices and
  consent belong to the customer who was responsible at the time (the `customer_id` is stored on
  the record, not derived from current ownership).
- **A booking request is not a customer record.** Guest submissions store what was typed in a
  snapshot. Linking a request to an existing customer is an explicit staff action after
  verification (BR-02). Nothing about an existing customer is ever returned to a guest.
- **Registration plates move.** Plates live in `vehicle_registrations` with validity periods. Search
  by plate resolves to the vehicle that held the plate at a given time (BR-04).

## 5. Assumptions

| #    | Assumption                                                                                           |
| ---- | ---------------------------------------------------------------------------------------------------- |
| A-01 | One garage location per deployment (see Q-01).                                                       |
| A-02 | Customers identify primarily by mobile phone; email is optional.                                     |
| A-03 | A single currency per garage; multi-currency invoices are out of scope.                              |
| A-04 | Object storage (Neon Object Storage or S3-compatible) holds files; the database holds metadata only. |
| A-05 | SMS (and possibly WhatsApp) is the main notification channel; providers are not yet chosen (Q-07).   |
| A-06 | PostgreSQL ≥ 18 (Neon), so `uuidv7()` is available natively.                                         |
